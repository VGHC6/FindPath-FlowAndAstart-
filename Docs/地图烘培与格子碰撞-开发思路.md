# 地图烘培 + 格子碰撞系统 —— 开发思路

> 状态：设计阶段，尚未实现
> 本文档放在 `Docs/`（`Assets/` 之外），避免 Unity 把它导入资源库、生成 .meta、打进包体。

---

## 一、目标

1. 做一个 **烘培工具**：把 3D 场景（地面 + 障碍物）烘培成 2D 格子图，存成资产。
2. 做一个 **格子碰撞系统**：烘培出的地图在运行时可以动态改变 —— 一个敌人占据的格子，其他敌人进不来，以此实现单位间的碰撞。

---

## 二、已确认的决策

| 项 | 决策 | 理由 |
|---|---|---|
| 碰撞方案 | **格子预约式**（非物理、非局部避让） | 确定性好，能保证不重叠 |
| 烘培产物 | **必须与静态数据分离，运行时绝不写回资产** | SO 资产是磁盘共享资源，运行时写入会落盘、跨 Play 会话共享 |
| 动态占用层归属 | **Model** | 运行时会变的状态（`IModel` 带 `ICanSendEvent`，正是为此设计） |
| 静态查询归属 | **Utility**（`IFlowFieldUtil`） | `IUtility` 无任何 `ICanGetXxx`，是刻意设计的最底层零依赖角色 |
| 烘培工具归属 | **不进架构**，放 `Assets/Editor/MapBaker/` | 它是 Editor 期逻辑，不参与游戏循环；项目无 asmdef，必须靠 `Editor` 目录名隔离 |
| 编排层归属 | **System** | 抢占裁决、两阶段移动、流场缓存都属于编排 |

### 分层落位

```
[Editor]     MapBakerWindow (EditorWindow)        ← 不在架构里，Editor/ 目录
                 │ 写出
[Data]       GridMapAsset : ScriptableObject      ← 静态只读资产（地形/障碍）
                 │ 运行时读取
[Utility]    IFlowFieldUtil                        ← 纯查询：方向 / 坐标转换 / IsWalkable
                 │
[Model]      IMapModel                             ← ★ 动态层：occupant（运行时可变）
                 │
[System]     IFlowFieldSystem                      ← 流场缓存 + 脏标记（只对地形变化重建）
             IAgentMoveSystem                      ← 两阶段移动、抢占裁决、卡死解锁
                 │
[Controller] MonoBehaviour                         ← 把 asset 交给 System，接输入
```

查询时两层 OR 起来：

```csharp
IsBlocked(x, y) = !asset.walkable[idx] || occupant[idx] != 0
```

## 三、待定决策（开工前必须定）

### ① cellSize 用 1.0（建议）

`Enemy.prefab:107` 的 SphereCollider `radius = 0.5`，**直径正好 1.0**。把 cellSize 从 0.5 改成 1.0，三件事同时变简单：

- **占用就是 1 格**，不需要 2×2 footprint
- **障碍不需要额外膨胀**：敌人中心在格心、离格边 0.5 = 半径；相邻障碍格从格边开始 → 正好相切、不重叠。数学上刚闭合
- **箭头尺寸顺手修对**：`pointTarget.prefab:32` 的 scale 0.1 × Plane 网格 10 单位 = 1×1 世界单位，在 cellSize=1.0 下正好是 1 格（在 0.5 的格子上它是 2×2 格，一直偏大）

代价：流场分辨率从 40×40 降到 20×20。但既然在做烘培工具，**改回去只需重烘一次**，不值得为它纠结。

> 通用结论：只要「单位在格子中的 footprint 尺寸（世界单位）= 它的直径」且中心落在 footprint 中心，相邻障碍格给出的间隙就恰好等于半径。所以 0.5 + 2×2 也正确，只是 1.0 + 1×1 的代码最简单。

### ② 玩家算不算格子？★ 最大的坑

现状是两套不兼容的移动方式：

- **敌人**：`InitController.cs:80` 直接改 `transform.position`，格子化，天然适配格子占用
- **玩家**：`PlayerController.cs:58-62` 是 **Rigidbody + AddForce 的物理移动**，完全不贴格子

两个选项：

- **(a) 全部格子化** —— 玩家也吸附格心、逐格移动。统一简单，但会丢掉物理/动画手感。MOBA 几乎不这么做
- **(b) 敌人格子化 + 玩家作为障碍** —— 敌人之间用格子互斥；玩家自身自由物理移动，但玩家所在格对敌人是阻挡。保留玩家手感，更接近真实 MOBA

**必须先定这一个**，它直接决定第 3、4 步的数据结构。

### ③ 烘培产物格式

建议 `ScriptableObject`（Inspector 可看、可视化调试最方便）。40×40 也就 1600 格，体积不是问题，**能看到数据比什么都重要**。

## 四、开发步骤

### Phase 0：定参数

完成第三节的三个决策。**不要跳过**：cellSize 和「玩家算不算格子」会渗透进后面每一层的代码。

### Phase 1：烘培工具

- 目录 `Assets/Editor/MapBaker/`
- 产物 `GridMapAsset : ScriptableObject`：

  ```
  int xSize, ySize;
  float cellSize;
  Vector2 origin;
  bool[] walkable;
  ```

  **origin / cellSize / 尺寸必须一起存进资产。** 现在是运行时从 `Renderer.bounds` 现算的（`FlowFieldUtil.cs:71-73`），烘培和运行时各算一次就会不一致 —— 这是「我明明烘过了为什么格子还是歪的」唯一的来源。

- 工具输入：地图对象 + 障碍物列表
- **明确指定用哪个 Collider**，不要再 `GetComponent<Collider>()` 随便挑第一个（`FlowFieldUtil.cs:235`）—— `obstacle1` 同时挂了 BoxCollider 和 MeshCollider
- 验收：在 Scene 里用 Gizmos 画出格子，肉眼确认；打印可行走格数

### Phase 2：静态层改成纯数据

- `Init(GridMapAsset)` 取代 `Init(GameObject, float)`（`FlowFieldUtil.cs:66`）
- **删掉** `AddObstacle`（`:86`）和 `WorldToGridRange`（`:233`）—— 烘培时已做完，运行时不再需要
- 保留 `IsWalkable` / `WorldToGrid` / `GridToWorld` / `GetDirection`
- 验收：`FlowFieldUtil` 内不再出现任何场景对象，只有数据进出

### Phase 3：动态占用层（Model）

- `IMapModel : IModel`，注册到 `mobaTest.cs:6-13`
- 核心是 **`int[] occupant`**（0 = 空，>0 = 单位 ID）。
  **用 `int` 不用 `bool`**：必须知道「是谁占的」，否则释放和裁决都做不了
- 接口：`TryClaim(x, y, id)` / `Release(x, y, id)` / `IsBlocked(x, y)`
- **裁决策略（谁抢赢）不放在 Model 里** —— Model 只管数据和原子操作，策略归 System

### Phase 4：移动系统（最关键的一步）

新 `IAgentMoveSystem : ISystem`，两阶段：

1. 所有单位算目标格 → `TryClaim`
2. **只有申请成功的才真正移动**

同时把移动方式换成 **朝目标格中心插值**，替换 `InitController.cs:80` 的 `position += direction * speed * dt`。

> 这一步一石二鸟：它同时就是「卡在障碍物边缘」的修复。连续积分会让单位停在格子中间的任意位置，「占哪格」是模糊的，跨边界时占用表闪烁、移动抖动。**吸附格心才能让占用表稳定。**

另外：遍历顺序必须按 ID 固定，不能依赖字典遍历序，否则「谁抢到格子」不确定。

### Phase 5：生命周期与死锁

- **敌人死亡 / 移除必须 `Release`。** 忘了释放 → 地图被幽灵格慢慢占满，症状是「越玩越卡」，极难排查
- **对向阻塞**：窄通道里两个敌人互相申请对方的格，会永久卡死。先做最简单的「等待重试 N 帧」
- 越界保护

### Phase 6：可视化

Gizmos 画三种颜色：**障碍格 / 占用格 / 每个单位的目标格**。

**不做这个就没法 debug 格子系统** —— 这一步投入产出比最高，别省。

### 已修复

| 问题 | 位置 | 修法 |
|---|---|---|
| 每格加载箭头导致崩溃 | `InitController.cs:54,56` | 循环边界误用 `GetMapSize()`（返回总格数 1600），实际跑了 1600² = 256 万次 Instantiate。已改用 `xSize` / `ySize` |
| 箭头方向几乎全是零 | `InitController.cs:59` 调 `GetDirection` | 形参名为 `gridPos` 但内部走 `WorldToGrid`，传入网格坐标时 93.75% 越界返回 `Vector3.zero`。已统一为世界坐标，接口形参改名 `worldPos` |
| 箭头旋转差 180° | `InitController.cs:64` | Unity 内置 Plane 的 UV 的 **v 轴朝 −Z**（官方 issue，拒绝修），贴图箭头默认指向 −Z。正确公式：`Atan2(-direction.x, -direction.z)` |
| 箭头与地面共面 z-fighting | `InitController.cs:69` | 生成位置加 `Vector3.up * 0.1f` |

> 注意：**把 Y 角度取负 ≠ 转 180°**。`Euler(0, -θ, 0)` 把 +Z 映射到 `(-sinθ, 0, cosθ)`，x 取反但 z 不变 —— 那是镜像不是旋转。要转 180° 必须把 `Atan2` 的两个参数同时取负。

## 六、其他备忘

### 为什么不要让流场吃 occupancy

如果让流场把动态占用也算进去，敌人一动流场就得重建，而且方向会来回抖（A 让开 → 路径变好 → B 又挤进来）。

正确做法：**流场只管地形（静态、可烘培、可缓存），单位之间的避让放在移动那一层（动态、每帧、局部决策）。**

### 流场是「以终点为中心」的

同一终点的所有单位共用一张流场，所以**单位数量几乎不影响开销**；真正决定开销的是 **不同终点的数量 × 重建频率**。所以：

- 敌人共用一张（追同一个目标）
- 玩家点击移动建议走 A\* + 路径跟随（单单位、终点频繁变）
- 多英雄追不同目标 → 每个终点一张，K 通常很小

### 代码组织

现在有两套并行代码：

- `Assets/Scripts/` —— 正式架构（Controller / System / Model / Utility）
- `Assets/ScriptsTest2/` —— `InitController` 那个流场试验场

**新代码应该进 `Assets/Scripts/`。** `InitController` 最后应退化成「把 asset 交给 System」的几行，否则它会同时承担初始化、敌人管理、移动逻辑，越滚越大。
